# تمرین ۳: ورود با کوکی، و شکستن آن

> جلسهٔ ۳ · مهلت: شب پیش از جلسهٔ ۴

## هدف

یک ورود ساده با کوکی نشست بسازید، خودتان با CSRF به آن حمله کنید، و بعد جلوی حمله را بگیرید. در پایان باید بتوانید بگویید مرورگر کوکی را همراه کدام درخواست می‌فرستد، `SameSite` دقیقاً کدام مرز را می‌کشد، و چرا CORS جای دفاع سرور را نمی‌گیرد.

## پیش از شروع، به این فکر کنید

سؤال آخر کلاس را به یاد بیاورید: کوکی نشست `SameSite=Strict` است و سرور شما روی `http://localhost:8000`. صفحهٔ مهاجم یک فرم پنهان دارد که خودکار به `/transfer` ارسال می‌شود. اگر صفحهٔ مهاجم روی `http://localhost:9000` باشد حمله موفق می‌شود؟ و روی `http://127.0.0.1:9000`؟ چرا؟ جواب نهایی را در سؤال `strict_sites` پایین می‌دهید.

## کار پایه

از `starter/server.mjs` (Node 22) شروع کنید، یا همین را با `http.server` در Python 3.11 بنویسید. از این تمرین به بعد ماژول HTTP زبان مجاز است، ولی کتابخانهٔ آمادهٔ نشست و چارچوب وب نه. سرور پورت را از آرگومان اول می‌گیرد و مقدار `SameSite` را از متغیر محیطی `SAMESITE` (پیش‌فرض `Lax`؛ مقدار `off` یعنی بدون این attribute).

| درخواست | پاسخ |
| --- | --- |
| `POST /login` با بدنهٔ فرم `user=ali` | `200` یا `303`، با `Set-Cookie` نشست: شناسهٔ تصادفی دست‌کم ۱۶ بایتی، `Path=/` و `HttpOnly` و `SameSite` |
| `GET /me` بدون نشست معتبر | `401` |
| `GET /me` با نشست | `200` با متن `user=ali balance=1000` |
| `POST /transfer` با بدنهٔ فرم `to=sara&amount=100` | بدون نشست `401`؛ با نشست `200` و موجودی کم می‌شود |
| `POST /logout` | نشست **در سرور** پاک می‌شود؛ همان کوکی دیگر کار نمی‌کند |
| `GET /` | یک صفحهٔ HTML با فرم ورود و فرم انتقال |

شناسهٔ نشست نباید از نام کاربر ساخته شود و دو ورود پیاپی باید دو شناسهٔ متفاوت بگیرند. هر کاربر موجودی خودش را دارد. سرور برای هر درخواست یک خط لاگ بنویسد: متد، مسیر، کوکی نشست داشت یا نه، و مقدار `Origin` و `Sec-Fetch-Site`.

خودآزمایی:

### حمله در مرورگر

این بخش نمره ندارد، ولی جواب سؤال‌های `answers.json` را با آن می‌سنجید. صفحهٔ `evil/index.html` را بنویسید: یک فرم پنهان به `http://localhost:8000/transfer` که با بار شدن صفحه ارسال می‌شود. آن را با `python3 -m http.server 9000` از پوشهٔ `evil` سرو کنید. در مرورگر خودتان در `http://localhost:8000` وارد شوید، صفحهٔ مهاجم را باز کنید و ببینید موجودی عوض شد یا نه:

| کوکی نشست | مهاجم روی `http://127.0.0.1:9000` | مهاجم روی `http://localhost:9000` |
| --- | --- | --- |
| `SAMESITE=off` | | |
| `SAMESITE=Lax` | | |
| `SAMESITE=Strict` | | |

اگر در Chrome نتیجهٔ `off` با `Lax` فرق داشت، دو دقیقه صبر کنید و دوباره امتحان کنید. لاگ سرور نشان می‌دهد کوکی همراه کدام درخواست رسید.

## چالش

- **دفاع دوم.** سرور `POST /transfer` را فقط وقتی بپذیرد که `Sec-Fetch-Site` برابر `same-origin` یا `none` باشد، یا این فیلد اصلاً نیامده باشد (کلاینت غیرمرورگر)؛ در غیر این صورت `403`. جدول بالا را دوباره امتحان کنید: حمله از `localhost:9000` هم دیگر نباید موفق شود.
- **اجازهٔ خواندن.** مسیر `GET /api/me` را اضافه کنید که با نشست معتبر JSON برگرداند و فقط `http://localhost:9000` بتواند با کوکی آن را بخواند: `Access-Control-Allow-Origin` دقیق، `Access-Control-Allow-Credentials: true` و `Vary: Origin`. به origin دیگر هیچ اجازهٔ CORS ندهید.

خودآزمایی کار پایه و چالش با هم: `node check/check.mjs 8000 --csrf`

## پرسش‌های answers.json

هر پاسخ آرایه‌ای از شماره‌هاست، مثل تمرین‌های ۱ و ۲.

| کلید | سؤال | گزینه‌ها |
| --- | --- | --- |
| `strict_sites` | کوکی نشست `SameSite=Strict` است، بدون دفاع دوم، و سرور روی `http://localhost:8000`. فرم پنهان صفحه‌ای روی کدام نشانی‌ها موجودی را کم می‌کند؟ | ۱. `http://localhost:9000` · ۲. `http://127.0.0.1:9000` · ۳. `http://127.0.0.1:8000` · ۴. صفحه‌ای روی خود `http://localhost:8000` |
| `csrf_defense` | کوکی نشست `Lax` است. کدام تغییر، به‌تنهایی، حملهٔ فرم پنهان از `http://localhost:9000` را ناکام می‌گذارد؟ | ۱. تغییر کوکی به `SameSite=Strict` · ۲. رد `POST /transfer` وقتی `Sec-Fetch-Site` برابر `same-site` یا `cross-site` است · ۳. نفرستادن `Access-Control-Allow-Origin` در پاسخ `/transfer` · ۴. token ضد CSRF در فرم انتقال، که صفحهٔ مهاجم نمی‌تواند بخواند |

## اگر خواستید بیشتر بدانید

این بخش‌ها نمره ندارند.

- در `/api/me` عمداً مقدار `Origin` را بازتاب دهید و از هر دو نشانی مهاجم در کنسول مرورگر `fetch(…, { credentials: 'include' })` را امتحان کنید. چه چیزی عوض شد و چرا خطرناک است؟
- ترافیک loopback را هنگام ورود ضبط کنید (`sudo tcpdump -i lo -A port 8000` در Linux، یا Wireshark) و خطی را پیدا کنید که کوکی نشست در آن دیده می‌شود. در یک شبکهٔ واقعی، چه کسانی می‌توانند همین خط را ببینند؟
- سامانهٔ نوبت‌دهی آزمایشگاه (موضوع پیش‌فرض پروژه) هم رابط وب دارد و هم API برای agent. نشست رابط وب با چه کوکی‌ای ساخته شود (نام، attributeها، عمر)، API با چه مدرکی کار کند، و چرا این دو را یکی نمی‌کنید؟

## پل به جلسهٔ ۴

کوکی نشست شما در این تمرین روی HTTP بی‌رمز جابه‌جا می‌شود؛ اگر ترافیک را ضبط کنید، آن را به‌صورت متن ساده می‌بینید. جلسهٔ ۴ دربارهٔ همین است: زیر HTTP چه می‌گذرد، و TLS دقیقاً چه چیزی را از چه کسی پنهان می‌کند.
