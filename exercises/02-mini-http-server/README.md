# تمرین ۲: سروری که HTTP را خودش می‌خواند

> جلسهٔ ۲ · مهلت: شب پیش از جلسهٔ ۳

## هدف

یک سرور HTTP/1.1 کوچک بنویسید که پیام را **خودش** از روی بایت‌های خام TCP بخواند؛ بدون ماژول http و بدون هیچ کتابخانهٔ HTTP. در پایان باید بتوانید بگویید یک پیام دقیقاً کجا تمام می‌شود و چرا مرز مبهم پیام خطرناک است.

## پیش از شروع، به این فکر کنید

لازم نیست جوابتان را جایی بنویسید یا تحویل بدهید.

اگر درخواستی هم `Content-Length: 4` داشته باشد و هم `Transfer-Encoding: chunked`، RFC 9112 دو راه پیش پای سرور می‌گذارد: درخواست را رد کند، یا طولش را فقط از روی chunked بخواند. در این تمرین راه سخت‌گیرانه را می‌خواهیم. چرا؟ اگر یک proxy جلوی سرور شما این درخواست را طور دیگری بخواند، چه اتفاقی می‌افتد؟

## کار پایه

از `starter/server.py` (Python 3.11) یا `starter/server.mjs` (Node 22) شروع کنید؛ فقط ماژول `socket` یا `net` مجاز است. سرور پورت را از آرگومان اول می‌گیرد و باید:

| درخواست | پاسخ |
| --- | --- |
| درخواست HTTP/1.1 بدون `Host` | `400` |
| `GET /` | `200` با HTML و `Content-Length` درست |
| `GET /hello?name=علی` | `200` با متن `سلام علی` و `Content-Type: text/plain; charset=utf-8` |
| `HEAD` روی هر مسیر GET | همان header‌ها، بدون بدنه |
| مسیر ناموجود | `404` |
| `DELETE /` | `405` با فیلد `Allow` |
| `GET /old` | `308` با `Location: /hello` |
| `POST /echo` | `200` و همان بدنه‌ای که فرستاده شد |

دو درخواست پشت‌سرهم روی یک اتصال باید دو پاسخ به همان ترتیب بگیرند. نام فیلدها به بزرگی و کوچکی حرف حساس نیست و `Content-Length` به **بایت** است، نه به حرف.

خودآزمایی:

## چالش

- درخواستی که هم `Content-Length` و هم `Transfer-Encoding` دارد، یا دو `Content-Length` متفاوت، باید `400` بگیرد و اتصال بسته شود. [RFC 9112 بخش ۶.۳](https://www.rfc-editor.org/rfc/rfc9112#section-6.3) برای حالت اول، خواندن فقط با chunked را هم مجاز می‌داند و تنها بستن اتصال را الزامی می‌کند. با خواندن همین بخش توضیح دهید چرا رد کردن امن‌تر است.
- مسیر `GET /visits` را اضافه کنید که به هر بازدیدکننده بگوید چندمین بار است این صفحه را می‌بیند، **بدون کوکی** و فقط با اطلاعاتی که در خود درخواست و اتصال هست، مثلاً نشانی IP کلاینت. آن را از دو دستگاه پشت یک مودم امتحان کنید. کجا اشتباه می‌شمارد و چرا؟

## پرسش‌های answers.json

هر پاسخ آرایه‌ای از شماره‌هاست، مثل تمرین ۱.

| کلید | سؤال | گزینه‌ها |
| --- | --- | --- |
| `visits_by_ip` | اگر شمارندهٔ `/visits` بازدیدکننده را با نشانی IP بشناسد، در کدام حالت‌ها اشتباه می‌شمارد؟ | ۱. دو نفر که از یک رایانهٔ مشترک در دانشکده وارد می‌شوند · ۲. دو دستگاه پشت یک مودم · ۳. یک مرورگر که صفحه را دو بار بارگذاری می‌کند · ۴. گوشی‌ای که از Wi-Fi به اینترنت همراه می‌رود و صفحه را دوباره باز می‌کند |
| `upstream` | جلوی این سرور یک proxy می‌گذارید. اتصال proxy به سرور با کدام گزینه، ابهام مرز پیام را از بین می‌برد؟ | ۱. HTTP/1.1، چون ساده‌تر است · ۲. HTTP/1.1 با `Transfer-Encoding: chunked` برای همهٔ پیام‌ها · ۳. HTTP/2، چون طول هر frame صریح است |

- خروجی خودآزمایی در `evidence/check.txt` باید از اجرای واقعی روی کامپیوتر خودتان باشد.

## اگر خواستید بیشتر بدانید

این بخش‌ها نمره ندارند.

مسیر `POST /orders` با فیلد `Idempotency-Key`: اگر همان کلید با همان بدنه دوباره آمد، همان پاسخ قبلی (با همان شمارهٔ سفارش) برگردد؛ اگر همان کلید با بدنهٔ دیگری آمد، `422`. با قطع عمدی اتصال پیش از خواندن پاسخ نشان دهید سفارش دو بار ثبت نمی‌شود.

برای سؤال `upstream`، پژوهش [HTTP/1.1 must die](https://portswigger.net/research/http1-must-die) را بخوانید و دلیل انتخابتان را در یک پاراگراف برای خودتان بنویسید.

## پل به جلسهٔ ۳

شمارندهٔ `/visits` نشان می‌دهد پروتکلی که هر درخواست را جدا می‌بیند، کاربر را به‌خودی‌خود نمی‌شناسد. جلسهٔ ۳ دربارهٔ همین است: state و هویت.
