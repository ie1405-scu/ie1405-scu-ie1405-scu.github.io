# تمرین ۲: کیف پول بوفه، از سوکت تا TLS

> جلسه‌های ۲ تا ۴ · مهلت: جمعه ۸ آبان ۱۴۰۵، ساعت ۲۳:۵۹

## در یک نگاه

| | |
| --- | --- |
| **چه می‌سازید** | یک سرور، در سه گام: خواندن HTTP از بایت‌های خام، ورود با کوکی، و اجرا روی TLS |
| **چه تحویل می‌دهید** | چهار فایل در پوشهٔ `ex02/` مخزن خودتان (فهرست در بخش «خودآزمایی و تحویل») |
| **چگونه نمره می‌گیرید** | تمام‌خودکار: کد شما با آزمون اجرا می‌شود و پاسخ دو سؤال چندگزینه‌ای با کلید مقایسه می‌شود |

## داستان

بوفهٔ دانشکده می‌خواهد پرداخت نقدی را کنار بگذارد. هر دانشجو یک کیف پول با ۲٬۰۰۰٬۰۰۰ تومان اعتبار می‌گیرد و پول ناهار را از آن به حساب بوفه منتقل می‌کند. سرور این سامانه را شما می‌نویسید، و این سرور همپای سه جلسهٔ گذشته رشد می‌کند:

| گام | سرور باید… | جلسه |
| --- | --- | --- |
| ۱ | HTTP بفهمد، بدون هیچ کتابخانه‌ای | ۲: یک تراکنش HTTP |
| ۲ | بداند چه کسی پول می‌دهد | ۳: state و هویت |
| ۳ | روی Wi-Fi دانشکده کوکی را لو ندهد | ۴: اتصال و TLS |

## پیش از شروع، به این فکر کنید

لازم نیست جوابتان را جایی بنویسید یا تحویل بدهید.

کوکی نشست یک دانشجو از گوشی‌اش تا سرور شما از دست چه کسانی می‌گذرد: نقطهٔ دسترسی Wi-Fi، مودم دانشکده، ارائه‌دهندهٔ اینترنت و هر proxy در راه. اگر ارتباط HTTP باشد، کدام‌یک کوکی را می‌بینند؟ و اگر HTTPS باشد، کدام‌یک؟

## آماده‌سازی

1. در مخزن خودتان پوشهٔ `ex02/` را بسازید.
2. یکی از `starter/server.py` (Python 3.11) یا `starter/server.mjs` (Node 22) را در `ex02/` بگذارید. نام فایل همین بماند.
3. فایل `starter/answers.json` را هم در `ex02/` بگذارید.
4. پوشهٔ `check/` را در `ex02/` کپی کنید. برای اجرای آن Node 22 لازم است، حتی اگر سرور را با Python بنویسید.

**ماژول‌های مجاز** فقط این‌هاست:

- برای اتصال: `socket` یا `net`
- برای گام ۳: `ssl` یا `tls`
- برای شناسهٔ نشست: `secrets` یا `crypto`

ماژول HTTP زبان، کتابخانهٔ نشست و چارچوب وب مجاز نیستند.

**اجرای سرور** این‌طور است:

| دستور | معنا |
| --- | --- |
| `node server.mjs 8000` (یا `python3 server.py 8000`) | سرور روی پورت ۸۰۰۰ |
| `node server.mjs 8443 --tls` | همان سرور روی TLS |
| `SAMESITE=Strict node server.mjs 8000` | مقدار `SameSite` کوکی؛ پیش‌فرض `Lax`، و `off` یعنی بدون این attribute |

**لاگ:** سرور برای هر درخواست یک خط لاگ بنویسد که این‌ها را نشان دهد: متد، مسیر، اینکه کوکی نشست داشت یا نه، و مقدار `Origin` و `Sec-Fetch-Site`. این لاگ نمره ندارد، ولی در بخش «مشاهده کنید» به آن نیاز دارید.

## گام ۱: سروری که HTTP را خودش می‌خواند

پیام را خودتان از بایت‌های خام TCP بخوانید و این پاسخ‌ها را بدهید:

| درخواست | پاسخ |
| --- | --- |
| درخواست HTTP/1.1 بدون `Host` | `400` |
| `GET /` | `200` با صفحهٔ HTML که فرم ورود (`/login`) و فرم انتقال (`/transfer`) دارد |
| `GET /hello?name=علی` | `200` با متن `سلام علی` و `Content-Type: text/plain; charset=utf-8` |
| مسیر ناموجود | `404` |
| `DELETE /` | `405` با فیلد `Allow` |
| `POST /echo` | `200` و همان بدنه‌ای که فرستاده شد |
| دو درخواست پشت‌سرهم روی یک اتصال | دو پاسخ، به همان ترتیب |

سه نکته را در نظر داشته باشید:

- نام فیلدها به بزرگی و کوچکی حرف حساس نیست.
- مقدار `Content-Length` به **بایت** است، نه به حرف.
- یک درخواست ممکن است در چند تکهٔ TCP برسد.

## گام ۲: سروری که شما را می‌شناسد

| درخواست | پاسخ |
| --- | --- |
| `POST /login` با بدنهٔ فرم `user=ali` | `200` یا `303`، با `Set-Cookie` نشست |
| `GET /me` بدون نشست معتبر | `401` |
| `GET /me` با نشست | `200` با متن `user=ali balance=2000000` |
| `POST /transfer` با بدنهٔ فرم `to=buffet&amount=150000` | بدون نشست `401`؛ با نشست `200`، و موجودی به همین اندازه کم می‌شود |
| `POST /logout` | نشست **در سرور** پاک می‌شود و همان کوکی دیگر کار نمی‌کند |

کوکی نشست باید این ویژگی‌ها را داشته باشد:

- شناسهٔ تصادفی دست‌کم ۱۶ بایتی، که از نام کاربر ساخته نشده باشد. دو ورود پیاپی دو شناسهٔ متفاوت می‌گیرند.
- سه attribute دارد: `Path=/` و `HttpOnly` و `SameSite`، با مقدار `SameSite` از متغیر `SAMESITE`.

دو نکتهٔ دیگر:

- هر کاربر موجودی خودش را دارد. کاربر تازه با ۲٬۰۰۰٬۰۰۰ تومان شروع می‌کند.
- فیلد `Cookie` ممکن است چند کوکی داشته باشد که با `; ` از هم جدا شده‌اند.

## گام ۳: همان سرور، روی TLS

با گزینهٔ `--tls`، سرور همهٔ مسیرهای گام ۱ و ۲ را روی TLS سرو می‌کند. گواهی و کلید را از مسیرهایی که متغیرهای محیطی `TLS_CERT` و `TLS_KEY` نشان می‌دهند بخوانید؛ پیش‌فرض آن‌ها `cert.pem` و `key.pem` کنار سرور است. خودآزمایی این دو متغیر را خودش تنظیم می‌کند و یک گواهی آزمایشی در `check/` دارد. برای اجرای دستی هم از همان دو فایل استفاده کنید:

</div>

```sh
TLS_CERT=check/cert.pem TLS_KEY=check/key.pem node server.mjs 8443 --tls
```

<div dir="rtl">

- **در Node:** اگر گام ۱ را درست نوشته باشید، این گام یعنی `tls.createServer` به‌جای `net.createServer`.
- **در Python:** این گام یعنی `ssl.SSLContext(...).wrap_socket` روی سوکت گوش‌دهنده.

## چالش

1. **مرز مبهم پیام.** درخواستی که هم `Content-Length` و هم `Transfer-Encoding` دارد، یا دو `Content-Length` متفاوت دارد، باید `400` بگیرد و اتصال بسته شود. [بخش ۶.۳ از RFC 9112](https://www.rfc-editor.org/rfc/rfc9112#section-6.3) برای حالت اول خواندن فقط با chunked را هم مجاز می‌داند. چرا رد کردن امن‌تر است؟
2. **دفاع دوم در برابر CSRF.** `POST /transfer` را فقط در این حالت‌ها بپذیرید: وقتی `Sec-Fetch-Site` برابر `same-origin` یا `none` است، یا وقتی این فیلد اصلاً نیامده، که یعنی کلاینت غیرمرورگر است. در غیر این صورت پاسخ `403` بدهید و موجودی را دست نزنید.

## سؤال‌های answers.json

هر پاسخ آرایه‌ای از شماره‌هاست، مثلاً `"strict_sites": [2, 3]`. ممکن است بیش از یک گزینه درست باشد.

**سؤال اول (`strict_sites`):** کوکی نشست `SameSite=Strict` است، بدون دفاع دوم، و سرور روی `http://localhost:8000` است. فرم پنهان صفحه‌ای روی کدام نشانی‌ها موجودی را کم می‌کند؟

1. `http://localhost:9000`
2. `http://127.0.0.1:9000`
3. `http://127.0.0.1:8000`
4. صفحه‌ای روی خود `http://localhost:8000`

**سؤال دوم (`rtt_reuse`):** کدام گزاره‌ها با مدل جلسهٔ ۴ و اندازه‌گیری شما سازگارند؟

1. درخواست تازه با TLS 1.3، بی‌احتساب DNS، سه RTT تا اولین بایت پاسخ لازم دارد.
2. درخواست دوم روی همان اتصال دو RTT صرفه‌جویی می‌کند.
3. درخواست دوم روی همان اتصال فقط یک RTT صرفه‌جویی می‌کند، چون handshake در TLS دوباره انجام می‌شود.
4. اگر پهنای باند دو برابر شود، زمان رسیدن اولین بایت درخواست تازه نصف می‌شود.

جواب این دو سؤال را با آزمایش‌های بخش بعد پیدا می‌کنید.

## مشاهده کنید (بی‌نمره، ولی برای جواب سؤال‌ها لازم)

**الف. حمله در مرورگر.** صفحهٔ `evil/index.html` را بنویسید: یک فرم پنهان به `http://localhost:8000/transfer` که با بار شدن صفحه ارسال می‌شود. آن را با `python3 -m http.server 9000` از پوشهٔ `evil` سرو کنید. در مرورگر در `http://localhost:8000` وارد شوید، صفحهٔ مهاجم را باز کنید و ببینید موجودی عوض شد یا نه:

| کوکی نشست | مهاجم روی `http://127.0.0.1:9000` | مهاجم روی `http://localhost:9000` |
| --- | --- | --- |
| `SAMESITE=off` | | |
| `SAMESITE=Lax` | | |
| `SAMESITE=Strict` | | |

اگر در Chrome نتیجهٔ `off` با `Lax` فرق داشت، دو دقیقه صبر کنید و دوباره امتحان کنید. لاگ سرور نشان می‌دهد کوکی همراه کدام درخواست رسید.

**ب. کوکی روی اتصال.** هنگام ورود، ترافیک را ضبط کنید: در Linux با `sudo tcpdump -i lo -A port 8000`، یا با Wireshark. خطی را پیدا کنید که کوکی نشست در آن دیده می‌شود. همین کار را با `--tls` روی پورت ۸۴۴۳ تکرار کنید. چه چیزی هنوز دیده می‌شود؟

**ج. زمان هر مرحله.** این بخش را روی یک سایت واقعی اجرا کنید، چون روی localhost زمان رفت‌وبرگشت تقریباً صفر است. چون هر دو URL در یک دستور آمده‌اند، curl برای دومی همان اتصال اول را دوباره به کار می‌گیرد. در Windows به‌جای `curl` بنویسید `curl.exe`.

</div>

```sh
curl -s -o /dev/null -w "dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n" https://www.rfc-editor.org/ https://www.rfc-editor.org/ > evidence/timing.txt
```

از داخل پوشهٔ `ex02/` این دستور را بزنید:

</div>

```sh

```

<div dir="rtl">

این دستور سرور شما را یک بار روی HTTP و یک بار روی TLS اجرا می‌کند، همهٔ آزمون‌های عمومی و چالش را می‌زند، و خروجی را در `evidence/check.txt` می‌نویسد. ساختار نهایی پوشه:

</div>

```text
ex02/
├── server.py  یا  server.mjs     ← کد شما
├── answers.json                  ← دو سؤال
├── evidence/
│   ├── check.txt                 ← خودکار، با node check/check.mjs
│   └── timing.txt                ← دستور curl بخش «ج»
├── AI.md                         ← فقط اگر از هوش مصنوعی کمک گرفتید
└── check/                        ← کپی خودآزمایی؛ بودن یا نبودنش فرقی نمی‌کند
```

پیش از مهلت، این‌ها را بررسی کنید:

- [ ] خروجی `node check/check.mjs` همان چیزی است که انتظار دارید.
- [ ] هر دو کلید `answers.json` پر شده‌اند.
- [ ] فایل `evidence/timing.txt` دو خط دارد.
- [ ] تغییرها روی شاخهٔ `main` push شده‌اند. محتوای `main` در پایان مهلت، تحویل نهایی است.

## نمره

کد شما در محیطی جدا و بدون اینترنت اجرا می‌شود. نمره از ۱۰ است:

| بخش | چه چیزی سنجیده می‌شود | نمره |
| --- | --- | ---: |
| گام ۱ | هفت آزمون جدول گام ۱، روی HTTP | ۲٫۵ |
| گام ۲ | شش آزمون جدول گام ۲، روی HTTP | ۲٫۵ |
| گام ۳ | آزمون‌های گام ۱ و ۲ روی TLS، به نسبت آزمون‌های قبول‌شده | ۱ |
| آزمون‌های پنهان | حالت‌هایی که در صورت تمرین گفته شده ولی خودآزمایی نمی‌زند، مثل درخواستی که در دو تکه می‌رسد | ۱ |
| چالش | چهار آزمون: دو مرز مبهم و دو حالت `Sec-Fetch-Site` | ۱ |
| `answers.json` | هر سؤال ۱ نمره؛ یک شماره اختلاف با کلید نیم نمره؛ جواب خالی صفر | ۲ |
| **جمع** | | **۱۰** |

- **نمره‌ای که در خودآزمایی می‌بینید:** همهٔ نمره جز آزمون‌های پنهان و `answers.json` است، یعنی از ۷.
- **فایل‌های `evidence/`:** باید از اجرای واقعی روی رایانهٔ خودتان باشند.
- **گفت‌وگوی کوتاه:** حدود یک‌پنجم تحویل‌ها به‌صورت تصادفی گفت‌وگوی پنج‌دقیقه‌ای دارند. بخشی را که نتوانید توضیح دهید، نمره نمی‌گیرد.

## اگر خواستید بیشتر بدانید

این بخش‌ها نمره ندارند.

- **شمارش بدون کوکی.** مسیر `GET /visits` را بسازید که بازدیدکننده را بدون کوکی و فقط با نشانی IP بشمارد. آن را از دو دستگاه پشت یک مودم امتحان کنید. کجا اشتباه می‌شمارد؟
- **اجازهٔ خواندن.** مسیر `GET /api/me` را بسازید که فقط `http://localhost:9000` بتواند با کوکی آن را بخواند. برای این کار `Access-Control-Allow-Origin` دقیق، `Access-Control-Allow-Credentials: true` و `Vary: Origin` لازم است. بعد عمداً مقدار `Origin` را بازتاب دهید و ببینید چه چیزی خطرناک می‌شود.
- **پروتکل بین proxy و سرور.** پژوهش [HTTP/1.1 must die](https://portswigger.net/research/http1-must-die) را بخوانید. اگر جلوی این سرور proxy بگذارید، اتصال proxy به سرور با HTTP/1.1 باشد یا HTTP/2؟

## پل به جلسهٔ ۵

درخواست دوم در `timing.txt` سریع‌تر بود، چون اتصال آماده بود. درخواست دوم برای یک تصویر از همان سرور شاید اصلاً به شبکه نرود. جلسهٔ ۵ دربارهٔ cache است.
